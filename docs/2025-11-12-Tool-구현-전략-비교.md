## 문제 정의

Agent Tool을 구현할 때 두 가지 접근 방식이 있다:

1. **Python 코드**: `@tool` 데코레이터로 함수 정의
2. **실행 파일**: 실제 디렉토리에 CLI 스크립트 배치

어떤 방식이 더 나은가? 아니면 혼합해야 하는가?

## 비교표

| 항목 | Python 코드 (`@tool`) | 실행 파일 (CLI) | 승자 |
|------|----------------------|----------------|------|
| **실행 속도** | ~0.1ms (함수 호출) | ~10-50ms (프로세스 생성) | 🏆 Python |
| **타입 안전성** | ✅ 타입 힌트, 자동완성 | ❌ 문자열만 | 🏆 Python |
| **디버깅** | ✅ Python 디버거 | ❌ stdout/stderr 추적 | 🏆 Python |
| **테스트** | ✅ pytest 단위 테스트 | ⚠️ 통합 테스트만 | 🏆 Python |
| **언어 독립성** | ❌ Python만 | ✅ 모든 언어 | 🏆 CLI |
| **Hot Reload** | ❌ 서버 재시작 필요 | ✅ 파일 수정만 | 🏆 CLI |
| **MCP 통합** | ⚠️ Python 래퍼 필요 | ✅ 직접 호출 가능 | 🏆 CLI |
| **확장성** | ❌ 제한적 (10-20개) | ✅ 무제한 | 🏆 CLI |
| **격리** | ❌ 같은 프로세스 | ✅ 독립 프로세스 | 🏆 CLI |
| **배포** | ✅ pip install | ⚠️ PATH 설정 | 🏆 Python |
| **버전 관리** | ✅ Git + pyproject.toml | ⚠️ 파일 버전 관리 | 🏆 Python |

## 실전 예시

### 예시 1: 간단한 파일 읽기

**Python 코드 방식:**
```python
@tool
def file_read(path: str) -> str:
    """파일 읽기"""
    return Path(path).read_text()

# Agent 호출
result = file_read("/tmp/data.txt")  # 0.1ms
```

**실행 파일 방식:**
```bash
#!/usr/bin/env python3
# /usr/local/bin/file-read
import sys
from pathlib import Path
print(Path(sys.argv[1]).read_text())

# Agent 호출
result = shell_execute("file-read /tmp/data.txt")  # 15ms
```

**결과**: Python 코드가 150배 빠름 ✅

**Python 코드 방식:**
```python
@tool
def hybrid_search(query: str, top_k: int = 5) -> str:
    """하이브리드 검색"""
    # Qdrant 연결
    qdrant = QdrantClient(...)
    # Neo4j 연결
    neo4j = GraphDatabase.driver(...)
    # 검색 로직 (50줄)
    ...
    return json.dumps(results)

# Agent의 함수 호출 공간에 이 거대한 도구가 들어감 → KV 캐시 오염
```

**CLI 방식:**
```bash
# /usr/local/bin/knowledge-search (100줄 스크립트)

# Agent 호출

# 장점:
# - Agent의 함수 공간은 shell_execute 하나만!

# - --help로 사용법 확인 가능
```

**결과**: CLI가 컨텍스트 효율적 ✅

### 예시 3: MCP 도구 통합

**Python 코드 방식:**
```python
# MCP 서버마다 Python 래퍼 작성 필요
@tool
def github_create_issue(title: str, body: str) -> str:
    """GitHub 이슈 생성"""
    # MCP 클라이언트 코드 (복잡)
    client = MCPClient(...)
    result = await client.call_tool("github", "create-issue", {...})
    return result

# 문제: MCP 도구가 50개면? → 함수 공간 폭발
```

**CLI 방식:**
```bash
# MCP를 CLI로 래핑 (한 번만)
# /usr/local/bin/mcp-cli

# Agent 호출
shell_execute("mcp-cli github create-issue --title 'Bug' --body '...'")
shell_execute("mcp-cli slack send-message --channel '#dev' --text '...'")

# 장점:
# - 함수 공간은 shell_execute 하나만!
# - MCP 도구 100개 추가해도 함수 공간 영향 없음
```

**결과**: CLI가 MCP 통합에 유리 ✅

## Manus의 하이브리드 전략 (추천)

Manus는 계층별로 다른 전략을 사용한다:

```
┌─────────────────────────────────────────────┐
│ Level 1: Python 코드 (@tool)               │
│ ─────────────────────────────               │
│ • 4-5개 atomic functions만                  │
│ • file_read, file_write, file_list          │
│ • shell_execute (유일한 관문!)              │
│                                             │
│ ✅ 장점: 빠름, 타입 안전, 디버깅 쉬움       │
│ ✅ 단점 없음: 개수가 적어서 (4-5개)         │
└─────────────────────────────────────────────┘
              ↓ shell_execute 호출
┌─────────────────────────────────────────────┐
│ Level 2: 실행 파일 (CLI)                    │
│ ─────────────────────────────               │
│ • knowledge-search (검색 CLI)               │
│ • mcp-cli (MCP 래퍼)                        │
│ • 무제한 확장 가능                          │
│                                             │
│ ✅ 장점: 유연함, 함수 공간 건드리지 않음    │
│ ⚠️ 단점: 느림 (10-50ms) - 괜찮음            │
└─────────────────────────────────────────────┘
              ↓ Python 스크립트 실행
┌─────────────────────────────────────────────┐
│ Level 3: Python 스크립트 (파일)             │
│ ─────────────────────────────────           │
│ • analyze_blog_network.py                   │
│ • process_large_dataset.py                  │
│ • 대량 데이터 처리                          │
│                                             │
│ ✅ 장점: 런타임 메모리, 요약만 반환         │
└─────────────────────────────────────────────┘
```

### 왜 하이브리드인가?

**Level 1을 Python 코드로:**
- 4-5개만 → 타입 안전성, 속도 이득 큼
- 자주 호출됨 → 0.1ms vs 15ms 차이가 누적
- 고정됨 → Hot Reload 불필요

**Level 2를 CLI로:**
- 무제한 확장 → 함수 공간 보호
- MCP 통합 → 래퍼 없이 직접 호출
- 자주 변경 → Hot Reload 유리
- 덜 호출됨 → 10-50ms 오버헤드 감수 가능

**Level 3를 파일로:**
- 대량 데이터 → 컨텍스트 오프로드
- 일회성 작업 → 속도 덜 중요
- 도메인 특화 → 유연한 수정 필요

## 성능 측정

### Level 1 (Python 코드)

```python
import timeit

# Python 함수 호출
timeit.timeit(lambda: file_read("/tmp/test.txt"), number=1000)
# → 0.1ms per call

# 1000번 호출: 100ms
```

### Level 2 (CLI)

```python
# 프로세스 생성
timeit.timeit(lambda: subprocess.run(["file-read", "/tmp/test.txt"]), number=1000)
# → 15ms per call

# 1000번 호출: 15,000ms (15초!)
```

**결론**: 자주 호출되는 도구는 Python 코드로!

### Level 2는 얼마나 자주 호출되나?

일반적인 Agent 세션 (50회 도구 호출):

```
file_read: 20회           → Python (0.1ms × 20 = 2ms)
file_write: 10회          → Python (0.1ms × 10 = 1ms)
shell_execute: 5회        → Python (0.1ms × 5 = 0.5ms)
  ├─ knowledge-search: 2회  → CLI (15ms × 2 = 30ms)
  ├─ mcp-cli: 1회          → CLI (15ms × 1 = 15ms)
  └─ python script: 2회    → CLI (20ms × 2 = 40ms)

총 시간: 88.5ms (대부분 Level 2 CLI)
```

**Level 2는 5회만 호출** → 85ms 오버헤드는 허용 가능!

## 프로젝트 적용 전략

### 디렉토리 구조

```
packages/agent-tools/
├── src/
│   └── agent_tools/
│       │
│       ├── level1/              # ← Python 코드
│       │   ├── __init__.py
│       │   └── core.py          # 4개 atomic tools
│       │
│       ├── level2/              # ← Python 코드 (CLI 진입점)
│       │   └── cli/
│       │       ├── knowledge_cli.py
│       │       └── mcp_wrapper.py
│       │
│       └── level3/              # ← Python 스크립트 (파일)
│           └── blog/
│               └── scripts/
│                   └── analyze_network.py
│
└── pyproject.toml
```

### pyproject.toml 설정

```toml
[project.scripts]
# Level 2 CLI 진입점 (설치 시 /usr/local/bin에 자동 배치)
knowledge-search = "agent_tools.level2.cli.knowledge_cli:main"
mcp-cli = "agent_tools.level2.cli.mcp_wrapper:main"
```

설치 후:

```bash
$ pip install -e packages/agent-tools

# 자동으로 CLI 생성
$ which knowledge-search
/usr/local/bin/knowledge-search

$ which mcp-cli
/usr/local/bin/mcp-cli

# Agent에서 호출 가능
shell_execute("knowledge-search search --query 'AI'")
```

### Level 2 CLI 구현 예시

```python
# packages/agent-tools/src/agent_tools/level2/cli/knowledge_cli.py

import click
import json

@click.group()
def main():
    """Knowledge base search utilities"""
    pass

@main.command()
@click.option('--query', required=True, help='Search query')
@click.option('--collection', required=True, help='Collection name')
@click.option('--top-k', default=5, help='Number of results')
def search(query: str, collection: str, top_k: int):
    """
    Semantic search in knowledge base

    Example:
        knowledge-search search --query "LangChain" --collection blog --top-k 5
    """
    from agent_tools.level3.blog.hybrid_retriever import BlogHybridRetriever

    # 검색 실행
    retriever = BlogHybridRetriever()
    results = retriever.search(query, top_k=top_k)

    # 결과를 파일로 저장 (Context Offloading!)
    import tempfile
    with tempfile.NamedTemporaryFile(mode='w', delete=False, suffix='.json') as f:
        json.dump([r.dict() for r in results], f, ensure_ascii=False, indent=2)
        output_file = f.name

    # 파일 경로만 출력 (Agent는 file_read로 읽음)
    click.echo(output_file)

if __name__ == '__main__':
    main()
```

**실행 흐름:**

```python
# Agent
result = shell_execute("knowledge-search search --query 'AI' --collection blog")
# → "/tmp/tmpxyz123.json"

content = file_read("/tmp/tmpxyz123.json")
# → 실제 검색 결과 JSON
```

## 실제 파일 vs Python 패키지

### 방식 A: 순수 실행 파일

```bash
# /usr/local/bin/knowledge-search (독립 실행 파일)
#!/usr/bin/env python3

# 문제:
# - 의존성 관리 어려움 (어떤 패키지 필요?)
# - 버전 관리 복잡 (Git에 바이너리?)
# - 배포 수동 (chmod +x, PATH 설정)
```

### 방식 B: Python 패키지 + entry_points (추천!)

```python
# packages/agent-tools/src/agent_tools/level2/cli/knowledge_cli.py
# (일반 Python 코드)

# pyproject.toml
[project.scripts]
knowledge-search = "agent_tools.level2.cli.knowledge_cli:main"

# pip install 시 자동으로 CLI 생성!
```

**장점:**
- ✅ 의존성 명확 (`pyproject.toml`)
- ✅ 버전 관리 쉬움 (Git)
- ✅ 배포 자동 (`pip install`)
- ✅ 테스트 가능 (`pytest`)
- ✅ 타입 힌트 유지

**Python 코드로 작성하지만, 실행은 CLI처럼!**

## 최종 결론

| Level | 구현 방식 | 이유 |
|-------|----------|------|
| **Level 1** | Python 코드 (`@tool`) | 4-5개만, 자주 호출, 속도 중요 |
| **Level 2** | Python 패키지 → CLI | 무제한 확장, 함수 공간 보호, MCP 통합 |
| **Level 3** | Python 스크립트 (파일) | 대량 데이터, 일회성 작업 |

### 핵심 인사이트

> [!quote] 하이브리드가 정답
> Level 1은 Python 코드의 장점 (속도, 타입 안전)을 취하고,
> Level 2/3는 CLI의 장점 (유연성, 확장성)을 취한다.
>
> 단, Level 2도 **Python 패키지로 작성**하되, `entry_points`로 CLI처럼 사용한다.
> 이렇게 하면 두 방식의 장점을 모두 가져올 수 있다.

### 구현 체크리스트

- [x] Level 1: `@tool` 데코레이터 (4-5개 함수)
- [x] Level 2: `click` + `pyproject.toml` scripts (CLI 진입점)
- [x] Level 3: 일반 Python 스크립트 (shell_execute로 실행)
- [x] 모두 `packages/agent-tools` 패키지에 통합
- [x] `pip install -e .`로 한 번에 설치
- [x] Git으로 버전 관리
- [x] pytest로 테스트
